# ADR 0013: The product runtime: a per-product environment, an install phase gated by the approved list, run_app, and a quality bar that reports what it could not run

- **Status:** Accepted (first slices; the Docker default and the registry allowlist enforcement follow in the same milestone)
- **Date:** 2026-10-13
- **Milestone:** M9 Dependencies + runtime (Product Mode, ADR 0007), issue #49

## Context
Until M9 a product could use nothing beyond the standard library: the sandbox set `PIP_NO_INDEX=1`, every command ran with SCIO's own interpreter, `delete_file` did not exist (a rejected new file was left empty), and `integrate` ran only the suite and lint. The planner's walking skeleton twice asked for a console-script install that nothing could perform (M8 live milestone). ADR 0007 component 4 asks for two phases, install with a registry allowlist and test offline, and component 5 for a quality bar with coverage, build, smoke and audit. The Claude Code backend (ADR 0012) adds a constraint: inside a Claude Code turn the sandbox's limits do not apply, so installs cannot be a worker-side act there.

## Decision
1. **A product environment per repository.** `ensure_product_env` creates `.scio/sandbox/venv` (git-ignored) with the profile's `venv_argv` and `--system-site-packages`, so the host's test runner and linter are visible without a download, and sets `Sandbox.python`; every sandbox rewrites `python` in an argv to that interpreter. The orchestrator calls it in `load`, before each feature and before `integrate` (idempotent: a resumed process has a fresh context).
2. **The install phase is a harness step with the network open for that call only.** `Sandbox.exec(..., network=True)` lifts the restriction for one command (`PIP_NO_INDEX` dropped on local, `--network bridge` on Docker); every other command keeps `limits.network`. The approved list is `PRODUCT.md`'s `## Approved dependencies`, which a human approved; `ensure_product_env` installs exactly that list. The profile's `index_allowlist` names the registry hosts; the local sandbox cannot enforce it (documented since M2), the Docker backend will through an egress proxy in a later slice.
3. **`install_deps` is a worker tool gated by the same list.** A package not on the list is refused with a message that tells the worker to set `needs_design_decision` and name the package, which is the human escalation the graph already has; the owner adds it to `PRODUCT.md`. In task mode (no `PRODUCT.md`) the tool refuses everything. Tools that need this context take a third argument (`ToolDef.needs_context`, `ToolBox.context`), so the tool registry stays data. Capabilities: `{mutation, untrusted_input}`, not `exfiltration`, because the destination is an allowlisted registry and the content is a human-approved list; the trifecta check still applies to the toolset as a whole.
4. **`run_app` starts the product and stops it.** `python -m <module> <args>` from the profile's `app_argv`, a local health URL polled until it answers, or the exit of a command that finishes; output tail returned; the process is terminated before the tool returns. Local sandbox only in M9 (the process runs on the host).
5. **`delete_file` on every backend** (`Sandbox.delete`, files only, never `.git`); the edit tool's revert of a rejected new file now removes it.
6. **The quality bar is profile data and reports honestly.** `checks:` in the profile (coverage with an 80 percent floor, wheel build, dependency audit) run after the suite and lint in `integrate`. A check whose tool is absent is reported as `skipped: tool absent`, never as a pass, and does not fail the milestone; a real failure does. The milestone gate and the PR body show every line. Coverage artifacts are in the profile's cache excludes.
7. **Acceptance runs against the started product.** `PRODUCT.md` carries a `## Runtime` section (`kind: cli|http`, module, start arguments with `{port}`, health path) that the planner fills and the normaliser checks (`AppSpec`); the scaffold ships `tests/acceptance/` with an `app_url` fixture that skips when nobody started the app, so the plain suite stays green; `run_acceptance` starts an `http` product on a free port, waits for its health path, runs those tests with `APP_URL`, stops the process and reports `[acceptance]` in the integration text; a `cli` product's tests run as they are.
8. **The walking skeleton never needs an installed entry point.** The planner prompt says so, and `_module_only_skeleton` in the normaliser rewrites a P1 criterion that names a console script, an entry point, an install, or a backticked command other than `python ...` into the `python -m <package> --version` form, with a note in the approval payload. Two live planners had written a console-script P1 that no sandbox could satisfy (M8 retrospective).
9. **The Claude Code backend installs outside the turn.** `install_deps` has no `--allowedTools` rule; `run_app` maps to the app command; the worker backend refuses a non-local sandbox.

## Consequences
- Tests: `tests/unit/test_runtime.py` (environment creation and reuse, the network switch, the approved-list gate, context plumbing, `run_app` against a local HTTP server and an exiting command), `tests/unit/test_aci_tools.py` (delete), `tests/unit/test_toolchain.py` (checks and outcomes), the product Fake tests (quality lines in the integration text, a clean tree after coverage).
- Every product build now creates a virtualenv on `load` (a few seconds) and the Fake product tests do too.
- The Fake `todo_api` product (`evals/product_scripts_http.py`: an http server whose approved dependency, `pyyaml`, the host already carries) runs through the whole loop offline: install phase, P1 and P2 through the task graph, the server started for the black-box acceptance tests, merge, a clean tree afterwards (`test_http_product_with_a_dependency_builds_and_passes_black_box_acceptance`).
- Open in M9: Docker default for product builds with a persistent container per build and the registry allowlist enforced by an egress proxy; a live milestone of an http product on the Claude Code backend.
