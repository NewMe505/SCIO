# ADR 0011: The milestone loop: the task graph as a subgraph, one thread per feature attempt, the orchestrator picks the work

- **Status:** Accepted
- **Date:** 2026-10-12
- **Milestone:** M8 Decompose + milestone loop (Product Mode, ADR 0007)

## Context
After M7 a repository exists with `PRODUCT.md` (features as black-box criteria, approved by a human) and `.scio/product/progress.json`. M8 turns the remaining features into merged milestones: group them, create the tracking issues, run each through the proven task graph, verify the integrated branch, open one PR per milestone for a human, and remember what happened so the next session continues from the repository alone. The M7 retrospective left one decision open: the planner's P1 (a walking skeleton with specific criteria) and the scaffold's skeleton are not the same thing, yet `progress.json` marked P1 done.

## Decision
1. **P1 is a feature run, not a scaffold side effect.** After bootstrap every feature in `progress.json` is `todo`, P1 included (`ProgressFile.initial`). The scaffold proves the toolchain; "done" means a feature run's own verify passed. The milestone planner's prompt says so, and the first milestone always starts at P1.
2. **A second graph, the same mechanics** (`scio/product/build.py`): `load -> plan_milestone -> issues -> feature* -> integrate -> milestone_gate -> [gate_decision] -> milestone_pr -> merge_wait -> update_progress -> plan_milestone | done` over `ProductBuildState`, compiled with the shared checkpointer, durability `sync`, thread `build-<product>` (one build thread per product; `scio build` resumes it until the product is done).
3. **The orchestrator picks the work; the planner proposes the grouping** (I-046). The next feature is always the first open one in `PRODUCT.md` order. The `milestone_planner` role (Opus, `MilestonePlanOutput`) proposes which open features form the milestone and a tier per feature; `normalise_milestone` keeps only a consecutive prefix starting at the first open feature, caps it at four, defaults tiers to T1 and records every change as a ledger note. The milestone branch is `milestone/<n>` from `main`.
4. **Tracking is idempotent by title.** With a GitHub client: `ensure_milestone("Mn: title")` and `ensure_issue("Pk: description", ...)` look up the title before creating, and each is wrapped in `run_effect` with a probe (`find_milestone`, `find_issue`). Offline: one Markdown file per feature under `.scio/product/issues/`, committed once on the milestone branch with a `[scio:issues:Mn]` marker.
5. **Each feature attempt is a task subgraph on its own thread.** `feature_context` derives a `RunContext` from the orchestrator's: the same sandbox (the product repository), effect log and prompts; a `Harness.child` with its own tier-pinned `BudgetGuard` and cost ledger; no GitHub client. The thread id is deterministic, `build-<product>-<pk>-a<attempt>`, so a crash mid-feature resumes the same subgraph (`thread_started` probes the checkpoint store); `run_graph`/`resume_graph` accept the orchestrator's open saver so both graphs share one store. The `TaskSpec` handed over carries the feature's criteria as acceptance, `milestone/<n>` as base branch, the issue number and the pinned tier. The task graph's `merge_wait` is answered by the orchestrator, which fast-forwards `milestone/<n>` to the feature branch (effect with an `is-ancestor` probe). Any other pause, or a non-success exit, becomes **one** product-level interrupt: `retry` (a new attempt, new thread), `skip`, or stop (`feature_failed`). The subgraph's own interrupt is closed with the same answer.
6. **Ground truth outranks the gate.** `integrate` runs the profile's full suite and lint on the milestone branch; a failure halts with `integration_failed` before any model is asked. `milestone_gate` (Opus, `GateOutput`) sees the features, each run's outcome, the integration output and a diff stat; a `pass` verdict is overridden to `escalate_human` when the checks failed or a feature is not `passed`. A non-pass verdict on green checks is one human question (`proceed` or stop).
7. **One PR per milestone, one human merge.** The PR body (cost per feature and for the orchestrator, escalations resolved/total, plan versus done, `Closes #n` per issue, the integration output, the gate verdict) is pushed with the branch and opened as a draft then marked ready; offline it is written to `.scio/product/milestones/Mn-pr.md`. `merge_wait` interrupts; `merged` with GitHub checks `pr_merged` and pulls `main` (asks again if the PR is still open); `merge` offline merges `--no-ff` with a `[scio:merge:Mn]` marker. `update_progress` records the milestone and its features (status, commit, thread, tier, issue, cost) in `progress.json`, prepends a line to `NOTES.md`, commits on `main` with `[scio:progress:Mn]`, and loops to the next milestone while features remain, unless the human answered `merge and stop`, in which case the thread ends after the record (the first live milestone needed a stop before the next one started spending). Threads are named per starting milestone, `build-<product>-m<n>`, and `scio build` starts a fresh thread (`-r2`, ...) when the one for the next milestone has already ended.
8. **Verify counts new files.** The first Fake build found that `git diff --stat <base>` ignores untracked files, so a feature delivered only by new files read as "no changes" (I-063). `diff_stat` now appends every untracked file and the full diff uses `git add -N` first.

## Consequences
- `tests/graph/test_product_build_fake.py` is the executable acceptance: a two-milestone Fake product (P1 at T0, P2 and P3 at T1) builds through the task graph with the product's own CI green on `main`; a crash at the gate of the second feature and a crash after the PR resume with no duplicated issue, commit, milestone or PR (offline files and a canned `gh` against a bare origin); a failing integration check or an unpassed feature overrides a passing gate verdict; an escalation inside P3 (repeated error, advisor, guided fix) is recorded on the product's `FeatureRun`, in the PR body and in the report; feature failures stop for one decision each (`skip`, `retry` on a new thread, stop); the milestone gate's escalation asks the human; the CLI (`scio build`, `scio status`, `scio report` on a `build-*` thread) works end to end.
- Costs: the orchestrator's own calls run under T1 caps as runaway guards; each feature under its tier's caps; the product has no cap (ADR 0007). `total_usd` (orchestrator plus every attempt) is in every interrupt payload and PR body.
- Open for M9: `integrate` runs tests and lint only; build, smoke against a running app, audit and the coverage floor arrive with the toolchain's runtime commands. The sandbox is still the local backend for product builds.
- Open: a feature that fails after a retry has no automatic path; the human decides each time. A `replan` verdict from the milestone gate is treated like `escalate_human` (one question) rather than re-running a feature.
