# ADR 0015: Product-ready: an honest quality bar, a release gate, and product evals graded black-box

- **Status:** Accepted
- **Date:** 2026-10-27
- **Milestone:** M11 Product-ready + evals (Product Mode, ADR 0007), issue #54

## Context
ADR 0007 decision 5 names the product-ready bar: tests with a coverage floor, lint and types, build, smoke and e2e against the running app, a dependency audit and a secret scan, README run instructions that work, and CHANGELOG, LICENSE and a release artifact. M9 and M10 built most of it as profile checks that `integrate` runs on the milestone branch. The read-only inventory for this milestone found four gaps and one structural flaw:
- the coverage floor was an argv literal, node had no coverage check, and `--cov` with no source counted the test files themselves (so "coverage passed" in the M9 live milestone partly measured tests);
- there was no secret scan, no README check and no check that the release files exist;
- the milestone loop ended at `done`, with no tag, release or artifact;
- the eval runner had no product suite and no way to grade a whole product from outside;
- every quality check ran only in `integrate`, after every feature had passed its own verify, so a miss halted the milestone with no node able to repair it (I-091).

## Decision
1. **The coverage floor is honest and is a setting.** `Settings.coverage_floor` (`SCIO_COVERAGE_FLOOR`, default 80) fills `{coverage_floor}` in the profiles' coverage commands (`QualityCheck.command`). It measures the product's own code run in the test process: the python scaffold sets `[tool.coverage.run] source` and omits the two-line `__main__.py`, the node check (Node's built-in `--experimental-test-coverage`) excludes `tests/**`. Code only a started process runs (the `serve` lifecycle) carries the stack's ignore comment (`# pragma: no cover`, `/* node:coverage disable */`); the black-box acceptance tests run it. Both scaffolds test their app in-process (node's `src/cli.ts` exports `createApp()`), so a fresh skeleton starts above the floor. Not chosen: subprocess coverage collection (per-stack plumbing; Node's runner does not merge child processes) and a lower floor.
2. **A check a feature is judged by runs in that feature's verify.** A profile check marked `verify: true` (coverage in both stacks, `typecheck` in node, since Node strips types and only `tsc` sees a type error) runs in every product feature's verify once tests and lint pass (`RunContext.quality_values`, set by `feature_context`). A miss is the failure kind `quality`, on the never-escalate list like `lint_only`, and goes to the debugger with the check's output and a hint about in-process tests. `build` and `audit` stay milestone-level. Task mode is unchanged (`quality_values` is None).
3. **Stack-neutral release checks are SCIO's own code.** `scio/product/release_checks.py`: a secret scan of the tracked files (prefixed token formats, private-key headers, and credential-named assignments whose value mixes letters and digits at high entropy; a line marked `scio: allow-secret` is skipped), the release files (README, CHANGELOG, LICENSE, Dockerfile), and the README's run block (`<!-- scio:run -->` to `<!-- scio:run-end -->`, each command starting with one of the profile's command words, no free-form shell). They always run; a finding fails the milestone. The product's own CI runs the same README block.
4. **Every scaffold ships a release image.** The profile's `release_image` lines (base image, how runtime dependencies are installed; profile data, I-093) plus the app's start command from `app_argv`; http skeletons read `HOST` so the container answers on its published port. CI's `docker-live` job builds and runs all four (python and node, cli and http).
5. **A release gate ends the build.** Once no milestone remains, `release_check` runs every `integrate` check on `main` and reads the version from the product's own skeleton command (`--version`); `release_decision` is the human stop (its own node, I-065); `release` cuts the product's changelog, tags `v<version>`, keeps a `git archive` of the tag (plus the build check's output) under `.scio/sandbox/release/`, and with `--gh` pushes the tag and publishes a GitHub Release with the artifacts. Every step is an effect with a world probe (ADR 0003). A failing check ends the build with `release_failed`; an existing tag ends it with nothing to do; `merge and stop` still ends at `done`. `main` is not pushed: like the progress commits, the changelog cut reaches GitHub with the tag. Not chosen: tagging without a human stop (publishing is outward-facing).
6. **Product evals are a fixed contract graded from outside.** A product task (`suite: product`, `grader: product`) carries a `PRODUCT.md` with the stack and the interface pinned, and a `hidden/` directory. `scio new --spec` bootstraps it as written (no interview, no planner); the solver builds every milestone to the release, answering the stops the owner would answer on a green build (`merge`, `release`, a green gate's `proceed`) and `stop` to anything else, every answer counted; then SCIO's own interpreter runs the hidden tests from a scratch directory against the released product (`APP_CMD`/`APP_DIR` for a CLI, `APP_URL` for a server started from `## Runtime`). Hidden tests are Python in every stack. Trial spend includes every feature's child harness (I-095). Not chosen: grading a free prompt (the planner picks the interface, so hidden tests could not know it).
7. **p003 is graded in a real browser** (the owner's choice, 2026-10-26): Playwright with headless Chromium in the dev group; CI's `checks` job installs the browser; elsewhere the browser tests skip.
8. **A pass that ran nothing is not a pass** (I-097). The profiles' `skipped_only` patterns (pytest's summary, TAP's counters) make `run_tests` report `no tests ran: every selected test was skipped`; verify fails a feature selection that only skipped, and the acceptance run and both graders fail an all-skipped run.

## Consequences
- Tests: `test_scaffold_coverage.py` (every fresh skeleton meets the floor), `test_a_feature_below_the_coverage_floor_is_fixed_inside_its_own_run`, `test_release_checks.py`, the release-gate tests (approve, decline, re-entry, idempotency, GitHub mode with a failed Release create resumed once), `test_product_evals_fake.py` (p001 and p002 pass, a stricter hidden test fails the same build, `scio new --spec` makes no model call, p003 in Chromium), `test_skipped_only.py`, the four Docker image tests in `docker-live`.
- Products bootstrapped before M11 counted their tests toward coverage and test through a child process; their next `scio build` may stop at the honest floor (`SCIO_COVERAGE_FLOOR` lowers it per run).
- A product feature's verify runs the suite once more (the coverage check); CI's `checks` job has a 25-minute budget from measured durations (I-094).
- The live product evals run on the Claude Code backend on the owner's Max login; their dollar figures are API-price estimates, not bills.
- Open: Docker for Node products' sandbox (the release image is not the sandbox image); `run_app` inside a container; the `--gh` path's `main` lags its local bookkeeping commits until the next milestone PR.
