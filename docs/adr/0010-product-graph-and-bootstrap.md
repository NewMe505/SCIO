# ADR 0010: The product graph: interrupts for humans, a normalised spec, an idempotent bootstrap

- **Status:** Accepted
- **Date:** 2026-10-12
- **Milestone:** M7 Greenfield bootstrap (Product Mode, ADR 0007)

## Context
ADR 0007 decided to add a product orchestrator above the task graph rather than rewrite it, with product memory in the target repository and a human approval at each product milestone. M7 is the first slice: `scio new` turns a prompt into a repository with green CI and a smoke test. It needs a second LangGraph graph with its own state, two model roles that did not exist (an interviewer and a product planner), human stops before any model output becomes a commitment, and a bootstrap that can be resumed after a crash without a second `git init` or a duplicate commit.

## Decision
1. **A separate graph, the same mechanics.** `scio/product/graph.py` builds `interview -> specify -> bootstrap -> [publish] -> done` over `ProductState` (defined in `scio/state/models.py`, so the checkpoint serializer's allow-list covers it). It is compiled with the same `open_checkpointer` and `durability` as the task graph and keyed by its own thread id (`new-<hex>`), so both graphs share one checkpoint store without touching each other.
2. **Every human stop is an `interrupt`.** The interview questions, the `PRODUCT.md` draft and the GitHub publish step each raise a JSON payload and resume with the human's text through `scio new --thread ID --decision "<text>"`. A prompt starts a thread, the absence of a prompt resumes one (I-061); `--thread` only names the thread. The interview is one interrupt with all questions; the answers travel as one text block to the planner. *Amended 2026-10-12 (I-065, M8):* each stop is a node of its own (`answers`, `approval`) after the node that made the model call, because a node re-runs from its start on resume; with the call and the interrupt in one node the first live resume ran the planner twice and approved a draft nobody saw.
3. **Two Opus roles, static prompts.** `interviewer` (two to four questions, `InterviewOutput`) and `product_planner` (`ProductSpecOutput`). Both are in `configs/models.yaml` and `scio/prompt/templates/`, their system prompts are static, and all per-run content goes in the user message, as every other role does.
4. **The planner's draft is normalised before anyone sees it** (`scio/product/spec.py`): the slug becomes a valid package name, an unknown stack falls back to `python` with a note, features are renumbered `P1..Pn`, a feature without an acceptance criterion gets a placeholder and a note, and a walking skeleton is inserted as `P1` when the planner left it out. The notes go into the ledger so the approval payload is honest about what was changed. The human sees the rendered `PRODUCT.md`; `approve` proceeds, anything else is a revision note the planner applies verbatim, and the third rejection halts the thread with `exit_reason = "rejected"`.
5. **Bootstrap is three effects with world probes** (`run_effect`, ADR 0003): `git-init` (probe: `.git` exists), `scaffold` (probe: `PRODUCT.md` on disk equals the approved text), `bootstrap-commit` (probe: a commit carrying `[scio:bootstrap]`). Between scaffold and commit the profile's lint and test commands run as ground truth; a failure halts with `bootstrap_failed` and nothing is committed. A second commit records the bootstrap sha in `.scio/product/progress.json`, so the marker commit itself never changes.
6. **The scaffold is per toolchain profile** (`scio/product/scaffold.py`): the `python` scaffold is a package with `--version`, one smoke test, a CI workflow that runs the profile's lint and test commands plus the version call, README, CHANGELOG, MIT LICENSE, `.gitignore` from the profile's cache excludes, `NOTES.md`, `PRODUCT.md` and `progress.json`. It installs nothing: the walking skeleton needs only the standard library and the profile's own tools. M10 adds a `node-ts` scaffold next to it.
7. **Publishing is a confirmed step.** With `--gh owner/name`, a fourth interrupt asks for `confirm` before `gh repo create --private --source . --push` runs as an effect (probe: an `origin` remote exists). Without `--gh`, the thread ends at `done` with a local repository.

## Consequences
- `tests/graph/test_product_new_fake.py` is the executable acceptance: an empty directory becomes a repository with green local CI (the profile's lint and tests run on the result, not a model verdict) and a passing smoke test; a crash-style resume after bootstrap duplicates nothing; three rejections halt; the normaliser's invariants hold; and the CLI contract works end to end on the Fake.
- The live acceptance is one `scio new` run on `sonnet_opus_advisor` from an empty directory, kept and read (cost by role in LESSONS_LEARNED).
- `scio report` still assumes `SCIOState`; product threads have no report yet (M8, when the milestone loop produces something worth reporting).
- The product graph has no cost cap of its own (ADR 0007 decision 5); the thread runs under the T1 tier caps as runaway guards, which is more than enough for two Opus calls and a scaffold.
- Open for M8: the milestone loop that consumes `progress.json`, decomposes `P2..Pn` into issues and runs each through the task graph with the tier pinned.
