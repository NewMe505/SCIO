# ADR 0014: A second stack proves the profile boundary: node-ts, profile detection, a stack-neutral product path

- **Status:** Accepted
- **Date:** 2026-10-26
- **Milestone:** M10 Second stack (Product Mode, ADR 0007), issue #51

## Context
ADR 0009 moved every Python-specific command and parser behind `Toolchain`, with `python` the only profile and detection left for M10. M7 to M9 then built Product Mode on top and, as the read-only inventory for this milestone showed, re-introduced Python in places the M6 boundary test does not scan: the scaffold (Python files only, `scaffold_for` raising for any other stack), the spec normaliser (`python -m <package> --version` literals, `python`/`pytest` as the only command words), the runtime (`VENV_DIR`, a `.pth` link, the `python` argv rewrite), the acceptance runner (`tests/acceptance`, a Python health probe), the toolbox (`run_tests` and `edit_file` never received the context's toolchain and defaulted to the python profile), the Claude Code allow-rules (`Bash(python -m pytest *)`), the planner prompt ("choose python") and every Fake script. `Settings.toolchain` knew one name and nothing detected a repository's stack. The M10 done criterion is the same product spec building in Python and in TypeScript.

## Decision
1. **One data-driven profile class.** `ProfileToolchain` (`scio/toolchain/profile.py`) holds every profile's data from `configs/profiles/<name>.yaml` plus a `StackParsers` set (the five functions that read a stack's tool output: failures only, summary present, error signature, removed public symbol, in-process syntax check). `python.py` keeps the Python parsers and is byte-identical in behaviour (`test_toolchain.py` unchanged); `node_ts.py` holds the TAP parsers. A third stack is a yaml file and a parser module. The registry knows both; `available_toolchains()` feeds the planner prompt.
2. **`node-ts` runs TypeScript on Node 22's type stripping with no download.** The test runner is `node --test` with TAP output (built in; "no test files" is exit 0 with `# tests 0`, a bad option is exit 9); `tsc --noEmit`, `tsc` build and `npm audit` form the quality bar and report `skipped: tool absent` until the product's own devDependencies are installed, like the python profile's coverage and build. eslint is the lint command with "Cannot find module" as its absent pattern. Not chosen: vitest (a download before the first test), JavaScript with JSDoc (no types), Docker for Node in this milestone (the sandbox image is Python).
3. **The protocol names what the product path needs.** `acceptance_dir`, `skeleton_command(name)`, `command_words`, `app_target(name, module)`, `syntax_check_argv(path)`, `health_probe_argv(url)`, `detect`. The normaliser, the acceptance runner, `run_app`, the Claude Code allow-rules and the scaffold read them; no `if stack == ...` remains in graph or product code. The toolbox context's toolchain reaches `run_tests` and `edit_file` (`needs_context`), and a toolchain passed directly is honoured too (I-082).
4. **`Runtime` describes the environment, not a venv.** `env_dir`, `env_marker`, an optional `env_create_argv` and an optional `env_interpreter`: a Python product has a virtualenv and its interpreter (the `.pth` link and the `python` rewrite as in ADR 0013); a Node product has `node_modules` that the first `npm install` creates and nothing rewritten. `normalise_package` reads npm specs (`zod@^3`, `@scope/name`).
5. **The syntax gate parses the way the loader loads.** `edit_file` runs the profile's `syntax_check_argv` after the write and before lint; for `node-ts` that is `module.stripTypeScriptTypes(source, {mode: "strip"})`, which rejects syntax errors and non-erasable TypeScript (parameter properties, enums) alike and executes nothing. `node --check` accepted a parameter property that then broke every import (I-083). The scaffold's `tsconfig.json` sets `erasableSyntaxOnly` so `tsc` agrees once installed; the planner prompt says "erasable syntax only".
6. **Detection by marker files, an explicit name wins.** `Settings.toolchain` defaults to `auto`: `resolve_toolchain` detects from the root's markers (`package.json` and `tsconfig.json` together before any Python marker) and falls back to `python`; `prepare_repo` adopts the clone's detected stack, `load` and `bootstrap` adopt `PRODUCT.md`'s declared one through `RunContext.adopt_toolchain`, which also re-points the sandbox's registry allowlist and the escalation policy's test directories. Detection goes through the sandbox's `exists`, so a Docker root is detected too.
7. **A stack-neutral acceptance contract.** Acceptance tests live in the profile's `acceptance_dir`, receive `APP_URL`, run with `test_argv(path=)` and are judged by `test_outcome`; an app started inside a non-local sandbox is probed with the profile's `health_probe_argv`.
8. **The local sandbox resolves bare commands on Windows.** `resolve_command` rewrites the interpreter word and finds npm's `.cmd` shims through `shutil.which`, because `CreateProcess` does not try `PATHEXT` (I-081); `LocalSandbox.exec`, `run_app` and `start_app` share it.
9. **The scaffold is a registry.** `scaffold_for` picks by `spec.stack`; `node_ts_scaffold` writes `package.json` (the product's dependencies, the quality tools as devDependencies), `tsconfig.json` (`nodenext`, `erasableSyntaxOnly`, `allowImportingTsExtensions`), `tsconfig.build.json`, an eslint flat config, `src/main.ts`, `src/cli.ts` (a `node:http` server for an http product), `src/version.ts`, `node:test` smoke and acceptance tests, CI with `setup-node`, and the common files.

## Consequences
- Tests: `tests/unit/test_toolchain_node_ts.py` (data, TAP outcomes from captured output, signature stability, exports, detection, tool resolution), `test_scaffold_node_ts.py` (the TypeScript skeleton runs, tests, lints, serves and passes acceptance; the syntax gate refuses a parameter property), the runtime and sandbox tests for the node environment and the win32 resolution, the normaliser test in both stacks, and `test_same_spec_builds_in_both_stacks`: the `todo_api` spec through the whole milestone loop in Python and in TypeScript on the Fake. Node-dependent tests skip without Node 22; CI installs it (`setup-node`).
- The Fake Node product has no third-party dependency: a Node product has no host environment to borrow from (the Python one borrows pyyaml through the `.pth` link), and the Fake runs with the network off. The install phase through `npm install` is exercised by the live milestone.
- `Runtime` field names changed (`env_*`); the python yaml follows. `Settings.toolchain` default is `auto`.
- Open: Docker for Node products (the sandbox image is Python); `run_app` inside a container; a lockfile for the install phase; the `test_` prefix in `escalation.py`'s drift rule is still Python-shaped (test directories cover Node).
