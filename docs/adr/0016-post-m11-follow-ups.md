# ADR 0016: Post-M11 follow-ups: GitHub-mode merges and releases, `scio upgrade`, a sandbox image for every stack, `run_app` in a container, parallel CI tests

- **Status:** Accepted
- **Date:** 2026-10-27
- **Milestone:** post-M11 follow-ups (Product Mode, ADR 0007), issue #58

## Context
ADRs 0013 to 0015 closed with open items, and the read-only inventory for issue #58 found two more defects in the `--gh` path:
- the `--gh` milestone loop pulled `main` with `--ff-only`, which a squash- or rebase-merged milestone PR breaks (I-102);
- the `--gh` release cut the changelog on local `main` and pushed only the tag, so the tag pointed outside `main`'s history and the last progress commit never reached origin (I-103);
- a product bootstrapped before M11 had no Dockerfile, no README run block and no coverage source, and nothing brought it up to the product bar except editing by hand;
- the sandbox image was Python only and the backend was chosen before `PRODUCT.md`'s stack was known, so a node-ts product would land in a container without Node (I-101);
- `run_app` refused any sandbox but the local one ("the process runs on the host");
- CI's test step ran serially in 789 s of a 25-minute budget, and grew with every product test.

## Decision
1. **A confirmed merge syncs `main` without assuming the merge style** (I-102). `sync_main` (`scio/product/build.py`) fetches origin and fast-forwards when local `main` is an ancestor of `origin/main`. Otherwise it resets local `main` to `origin/main` only when every local-only commit carries a SCIO bookkeeping marker (`[scio:progress:`, `[scio:release:`) and origin's `progress.json` still records the milestones those commits recorded; anything else raises `SyncRefused`, and the build halts `sync_failed` naming the commits. A human's commit is never dropped.
2. **A `--gh` release goes through a release PR**, as SCIO's own releases do (CONTRIBUTING step 6; I-103). `release` cuts the changelog on `release/<tag>` from local `main` (which carries the last progress commit), pushes it and opens a ready PR; `release_merge_wait` is its own node (I-065) that stops until GitHub reports the PR merged, then syncs `main`; `release_publish` tags `main`'s head, keeps the artifacts, pushes the tag and publishes the GitHub Release. Nothing pushes `main`, so a protected `main` works. Offline, the cut stays a commit on `main` and `release_publish` tags it. `ReleaseRecord` gains `pr_number` and `pr_url`.
3. **`scio upgrade --product DIR` is additive and generated from the current scaffold** (`scio/product/upgrade.py`). For the product's own `PRODUCT.md` it adds what is missing: the Dockerfile and `.dockerignore`, the README's marked run block under its `## Run` heading, `[tool.coverage.run]` for a python product, and the CI's README run step while the CI is still the old scaffold's. Anything the product made its own is kept and reported. A clean tree is required, the change is one commit with the marker `[scio:upgrade:<version>]`, and a second run does nothing.
4. **One sandbox image for every stack, probed for a capability** (I-101). `docker/sandbox.Dockerfile` copies Node 22 from `node:22-slim` next to Python (one image, because the egress proxy runs this image's python). Each profile names a `sandbox_probe` (python: 3.12 or later; node-ts: Node with TypeScript type stripping, a capability rather than a binary), exposed as `Toolchain.sandbox_probe_argv`; `docker_product_ready` runs it inside the image, and `scio build` reads `PRODUCT.md`'s stack before choosing the backend, so a product never lands in an image that cannot run it (it falls back to local and says why).
5. **`run_app` runs the app where the sandbox runs.** The app-start code moves from `scio.product.acceptance` to `scio.aci.apps`, which the acceptance run and the worker's `run_app` share: a host subprocess on a local sandbox; on any other a detached process under the wrapper `nohup sh -c '<app> & echo $! > app.pid; wait $!; echo $? > app.exit'`, probed with the profile's health command from inside, stopped by pid. The pid file holds the app's own pid, so stopping frees its port, and "exited" means the exit file exists, with the real exit code in it, which `run_app` reports. A crashing app also ends the acceptance run's health wait early, where it used to wait out the timeout.
6. **SCIO's own commits carry SCIO's identity** (I-104). `SCIO_GIT_IDENTITY` (`-c user.name=scio -c user.email=scio@users.noreply.github.com`, `scio/aci/tools.py`) is passed by `git_checkpoint`, the build's and the upgrade's git helpers and the bootstrap commits, so a product clone or a machine without a git identity (a CI runner, a fresh container) builds and upgrades. The test suite runs with git as CI sees it (an autouse fixture: an empty global config and `user.useConfigOnly=true`).
7. **CI runs the tests in parallel.** pytest-xdist joins the dev group; the `checks` job runs `pytest -n` at twice the runner's cores (the tests wait on git, subprocesses and node more than on CPU). Measured on 4-core runners: 789 s serial, 314 s in parallel, same counts. The local pre-push check stays serial (CLAUDE.md).

## Consequences
- Tests: `test_github_mode_survives_squash_merged_milestone_prs` (real squash merges on a bare origin for M1, M2 and the release PR; the old code fails with `git pull -q --ff-only origin main failed`), `test_github_mode_never_drops_a_human_commit_on_local_main`, the GitHub-mode release tests (no tag or Release before the merge, "not merged yet" when asked early, the tag on origin `main`'s head), `tests/unit/test_upgrade.py`, `tests/unit/test_product_sandbox_backend.py` (the probe per stack), `test_run_app_on_a_non_local_sandbox_*` in `tests/unit/test_runtime.py`, and in docker-live `test_a_node_product_installs_and_tests_inside_the_container` (a real `npm install` through the allowlist proxy and `node --test` on TypeScript inside the container) and `test_run_app_starts_probes_and_stops_inside_the_container`.
- Live: `scio upgrade` brought `bookmarks_api` (bootstrapped in M9) to the product bar in one commit, and its next `scio build` built milestone M2 on the Claude Code backend: P5 to P7 passed, every integration check passed, including the upgraded release files and README run block, and acceptance passed against the started server ($4.56 estimated at API prices, nothing billed).
- Bookkeeping commits, merges and tags in a product are authored `scio` even where the machine has an identity; the worker's checkpoints already were.
- Open: a lockfile for the install phase; the `test_` prefix in `escalation.py`'s drift rule; the Claude Code worker backend still runs on the host, so its features use the local sandbox.
